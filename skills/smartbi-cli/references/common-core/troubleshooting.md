# 分层排障

先确定失败所在层，再处理连接、请求参数或查询逻辑。

## 运行环境

检查 CLI 安装、所选连接及工作目录权限。缓存或文件权限错误按实际错误报告，不通过删除锁、重置全局配置或改写缓存位置绕过。查询请求与运行环境问题分别处理。

## 直接取数耗时

直接 MQL／SQL 取数较慢时，先比较 CLI 总耗时与响应中的 `durationMs`。按当前 CLI 契约确认该字段的计时范围；不要把两者差值直接认定为纯 CPU 时间。

总耗时高而业务 HTTP 耗时低时，用有界诊断检查 CLI／Registry 层。后续一次调用变快不能解释前一次慢的原因。不要自动加 `--refresh`、删除缓存或锁、修改全局缓存设置，或反复查询掩盖偶发延迟。同一任务复用已确认契约与元数据；有变化或失效证据时才刷新。连接建立阶段超时约10秒，不受单次 `--timeout` 控制；响应阶段按 `--timeout`/timeoutMs 判断。原生查询、网络和服务端处理耗时需借助服务端链路追踪区分。

调用工具等待超时不等于 CLI 请求已失败或成功。若仍有运行中的进程或会话，应在有界时间内继续等待同一次执行，不启动重复查询。输出重定向到文件时，先确认原进程结束，再解析完整 CLI 响应和业务状态；仅有文件或部分字节不算成功。只有结果已知，或能确保不会产生重复工作时才重试。预计较慢的查询应根据本次任务选择合适超时，不强制后台运行、固定等待数分钟或使用通用耗时基线。

## 认证、权限与业务失败

- 401：核实当前地址、serverType、凭证来源及目标环境令牌；仅设置环境变量不保证当前 profile 使用它。不要改SQL/MQL参数来修复认证。
- 403：区分操作权限和资源权限，按当前账号核实。
- `BIZ_ERROR`（exit 4）：CLI识别的顶层业务失败，流式同样检查；查看details中的上游错误，不作为网络问题重试。
- HTTP 200 但业务失败：检查 CLI `ok`、业务 `success/error`、接口的内部状态，不能按传输状态宣称完成。
- 资源、字段或参数问题：先核实真实资源类型和当前契约；空目录、空字段树、零行和接口不支持分别处理，不把单模型问题推广到所有模型。
- 只有文件或部分输出不代表执行完成。保留同一次请求标识，先核实进程或会话状态，再决定是否重试。

## 最小诊断信息

按当前失败层收集CLI版本、所用地址、操作名、HTTP与业务错误、tid、耗时以及脱敏请求结构。文件问题增加实际格式与大小，避免收集无关日志。不要输出令牌、Cookie、签名下载地址或完整凭证配置。
