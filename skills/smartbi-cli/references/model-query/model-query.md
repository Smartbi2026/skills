# SmartBI 模型查询接口与执行

使用目标环境已注册的 OpenAPI 操作及当前 `describe` 契约。下列请求仅展示结构；模型、来源、字段和筛选均须根据当前元数据与用户问句确定。

## 模型类型与查询对象

| 目录类型 | 处理方式 |
|---|---|
| `AUGMENTED_DATASET` 数据模型 | 对已选接口核实当前类型支持；元数据、JSON、MQL、SQL 分别见下方对应小节 |
| `TABULAR_DATASET` 指标模型 | 按场景选择结构化查询，核对当前部署与对象的实际支持；不自动换路 |
| `MT_MODEL` 新指标模型 | 核实子资源；若有 `MT_DATAMODELS`，选择包含目标指标和维度的关联 `AUGMENTED_DATASET`，再按其类型执行；不默认取第一个 |

新指标模型根 ID 不等于关联数据模型 ID。部署如提供专用查询能力，须核实契约与用户指定方式；没有有效映射时说明限制。资源定位与枚举类型见[公共资源发现](../common-core/resource-discovery.md)，不调用白泽清单替代模型目录。

## 资源定位与查询元数据

本文件说明模型定义与请求结构；查询方式由[模型场景](../../scenarios/model-query.md)决定。元数据用于确定字段、参数、来源和计算口径，再构造 JSON、MQL 或 SQL 请求，不因查询方式不同而重新探索一套元数据接口。

模型身份未核实时先按[公共资源发现](../common-core/resource-discovery.md)取得真实 ID 和类型。`smartbi list` 列出的是 API，不是模型；不通过空 `modelIds` 的字段树枚举资源。新指标模型先解析关联可查询对象，再获取其定义。当前环境的操作契约已确认时直接调用；否则先 `describe` 已知操作，不遍历无关接口。

### 统一入口与补充条件

`tabularmodel.getSimpleDataSet` 是数据模型、指标模型共用的普通查询元数据入口；`tabularmodel.getDataSet` 是两者共用的完整模型定义来源。两者请求相同：

```json
{"req":{"dataSetId":"<MODEL_ID>"}}
```

- **普通查询或只看字段、参数清单**：读取 `getSimpleDataSet` 的 `views`、`relations`、`dimensions`、`measures`、`parameters`。已有足够信息则直接使用，不重复获取。
- **明确需要完整定义**：直接使用 `getDataSet`；已知本次需要精简定义未提供的信息时，不必先调用精简接口。已有精简定义但仍有具体缺项时，只补一次完整定义。
- **接口不可用或返回不足**：核对当前契约与具体缺项；不能把调用成功当作信息完整，也不能把未返回的属性当作没有对应配置。

| 本次需要的信息 | 获取与使用规则 |
|---|---|
| 普通字段、维度层级、度量及聚合、逻辑视图与关系、参数清单 | 先用精简定义；读取实际返回的名称、别名和引用关系，不猜物理名称 |
| 时间快算需要的维度 ID、完整列计算、命名集、完整关联方向或参数配置 | 用完整定义，检查相关 `dimensions`、`views`、`measures`、`relations`、`namedSets`、`parameters`；不要求顺序读取全部内容 |
| 参数默认配置、是否默认生效及参数依赖 | 用完整定义的 `parameters`；精简结果的 `null` 不代表无默认配置。需要默认值或候选值的实际结果时，按下方参数取值规则调用专用接口 |
| 字段全路径、参数必填状态，或字段/参数成员信息 | 对当前契约支持的资源类型按需用 `dataset.getDataSetMetaData`；不能当作所有模型统一入口，也不能用空 `relations` 否定模型定义中的关联 |
| 筛选成员的实际值或显示值与编码的对应关系 | 复用已确认值；未确认时按接口实际能力获取成员，或做有界分组查询。模型定义不等于实际成员数据，动态参数候选配置也不等于已求得候选值 |
| 定义仍不足以表达的字段目录层级 | 才补 `datamodel.getDataModelTrees`；它不承担参数、默认值、关系及完整计算定义的获取 |

`dataset.getDataSetMetaData` 请求为 `{"resourceId":"<MODEL_ID>","resourceType":"<已核实类型>"}`，按需传 `fieldIds`、`paramIds` 加载成员。当前类型枚举不含 `TABULAR_DATASET`，不得强行套用。读取 `fields`、`params` 及实际成员返回；契约声明某属性不保证当前模型会返回有效值，成员为空不能直接证明模型无数据。

字段树请求为 `{"modelIds":["<MODEL_ID>"]}`，必须使用经目录核实的非空 ID。空数组不是列出全部模型；非空 ID 返回空树也不能单独证明资源不存在或无权限。空的 `augmented_params` 目录不能证明模型没有参数，参数以模型定义或适用的参数元数据为依据。

### 构造查询前的核对

只核对本次查询所需的信息：模型身份与类型、字段及统计方式、来源与必要关系、模型参数和成员筛选。三种请求的标识与参数位置不同：

| 查询方式 | 字段引用 | 模型参数位置 |
|---|---|---|
| JSON | `rows`、`columns`、筛选及排序使用查询用定义确认的字段名称，不用显示别名或字段 ID 替换 | `req.query.paramValues`，以参数 `name` 为键、已确认的值为值 |
| MQL | `dims` 使用已确认的层级路径，`metrics` 使用可查询度量标识；来源按 MQL 契约处理 | `req.params`，元素为 `{name, values}` |
| SQL | 从定义解析逻辑视图与列的查询别名，保留指标公式及聚合口径 | `req.params`，元素为 `{name, values}` |

模型参数使用定义中的 `name`，不使用展示别名或参数 ID。业务字段筛选与模型参数不是同一概念，不能互相替代。需要用户提供的参数尚未确定时澄清；已确认无须传值或可使用模型默认配置时才省略，不因参数清单非空就一律要求用户输入。

参数取值不明确时，使用 `tabularmodel.getParameterDefaultValue` 或 `tabularmodel.getParameterStandbyValues`；两者请求为 `{"req":{"dataSetId":"<MODEL_ID>","parameterName":"<PARAMETER_NAME>"}}`，有级联依赖时按契约追加已确认的 `parameterValues`。分别读取 `parameterValue` 或 `data` 中的 `value`、`displayValue`，不能把完整定义中空的默认配置当作没有运行时默认值。

参数候选的 `value` 与 `displayValue` 分别表示原始值和显示值。按当前接口明确的取值约定，从候选映射取得所需表示及类型；不能混用参数名称、显示别名和参数值。约定缺失或与运行时不符时报告契约问题，不通过更换值、加引号或遍历候选来试出可用请求。

精简定义可能列出度量却未列出其引用的底层视图列。JSON/MQL 可按已核实的度量标识查询；SQL 需要自行表达该度量时，须从完整定义补齐来源列及公式后再构造，不能把度量名称直接当作同名 SQL 列，也不把模型已聚合的结果再次随意聚合。

完整定义可能包含隐藏字段或辅助度量；读取完整定义不扩大可查询字段范围。结合查询用精简定义、隐藏状态及当前权限确认，不把内部字段直接作为面向用户的指标。缺少必要参数或存在业务歧义时澄清；无法取得必要定义或动态值时说明限制，不通过猜值执行。

同一任务中环境、身份和定义仍适用时复用元数据；不持久化模型缓存。SQL Overview 不是固定前置，也不做每次查询的 CGI 探测。

## 结构化查询（JSON）

`tabularmodel.queryDataSetDataIterator` 的 SDK 契约覆盖 `AUGMENTED_DATASET` 数据模型和 `TABULAR_DATASET` 指标模型，不是旧指标模型专属接口；实际可用性仍须结合当前对象的返回结果判断。选路已确定使用 JSON 后执行本节。该接口同时承担明细与汇总，请求按所需记录粒度构造，不先尝试其他查询接口。

按上述统一元数据规则核实字段名称、别名和类型，再构造 `req.dataSetId`、`req.requestId` 和 `req.query`。展示字段必须放入 `query.rows` 或 `query.columns`；指标通常放入 `columns`，维度也可按交叉表布局放入任一区域。`fieldProperties` 只为已声明字段追加聚合等属性，不会自动增加字段。筛选、模型参数、排序与分页均按该接口自身契约构造，不照搬 MQL 请求体。

明细查询须核实当前模型支持的清单 `queryType` 与查询引擎，保留业务记录粒度；不要固定套用聚合查询类型，也不自动开启去重。汇总查询按模型指标、分组和聚合定义构造。`quickCalculations` 的计算名称需加入 `columns`，时间类快算须匹配行区时间层级、`timeType` 与 `timeHierId`。从完整模型定义读取对应时间维的 `id` 作为 `timeHierId`，不把时间层级字段名、维度 `name` 或显示别名直接当作该标识；目标版本明确要求其他标识时须有对应契约依据，不能遇错后遍历猜值。`custom.items` 使用 MDX，不能直接填 SQL 计算列表达式；嵌套计算也须核实当前模型和引擎支持。

结果按 `iterator` 单元格及该接口分页状态处理，不能套用 `dataTable` 的行数规则。单元格计算使用 `value`，展示可使用 `displayValue`；同样核对筛选、粒度和完整性。迭代器返回结构不等于接口提供原生逐行数据流。

按 `rowPageNum`、`rowsPerPage` 和稳定排序翻页；`nextPageState=-1` 不表示已取齐，`totalRowCount=-1` 也不是实际总数。依据当前契约的有效总数或短页等结束证据判断完整性，并核对重复组与可加指标总额。

按用户条件的原始逻辑构造筛选：`filters` 表达 AND 条件，`relationNode` 表达所需的 AND/OR/NOT 条件树，两者按契约二选一；明确的集合包含条件使用 `IN`。保留括号、成员编码及 NULL 语义。接口拒绝符合契约的条件树时，记录脱敏请求和原始错误并报告接口异常，不为规避错误自动将 OR 改成 IN、拆分查询或改换接口。

### 指标模型的结构化查询

对已核实的 `TABULAR_DATASET` 按上述统一规则获取模型定义，不另设指标模型元数据流程。按当前 `describe` 构造 `tabularmodel.queryDataSetDataIterator` 的 `{"req":{"dataSetId":"<MODEL_ID>","requestId":"<REQUEST_ID>","query":{"rows":["<已核实的维度名>"],"columns":["<已核实的指标名>"],"rowPageNum":1,"rowsPerPage":100}}}`，筛选、分组、排序及结果迭代器均以该接口契约为准。不能套用增强数据集的 MQL/SQL 请求体或 `dataTable` 行数规则；查询成功后仍须校验当前模型的结果。

字段布局、单元格取值和分页使用上方 JSON 通用规则，不因资源类型不同另设一套。

## SQL

操作：`datamodel.queryDataBySql`
HTTP: `POST /api/v1/datamodel/datamodel/query-data-by-sql`
请求体：外层为 `req` 对象：

```json
{
  "req": {
    "modelId": "<MODEL_ID>",
    "modelType": "<MODEL_TYPE>",
    "sql": "SELECT year(\"<DATE_COLUMN>\") AS \"年\", SUM(\"<ADDITIVE_MEASURE>\") AS \"<ADDITIVE_MEASURE>\" FROM \"<LOGICAL_TABLE>\" WHERE \"<DATE_COLUMN>\" >= DATE '2025-01-01' AND \"<DATE_COLUMN>\" < DATE '2026-01-01' GROUP BY year(\"<DATE_COLUMN>\") ORDER BY \"年\" LIMIT 100",
    "params": [],
    "extraTables": [],
    "showDataTable": true
  }
}
```

`sql` 是针对模型逻辑表的只读 DuckDB SQL。根据当前模型定义确认逻辑视图别名、查询可见列别名及关联；技术列名或底层物理表名不能直接当作 SQL 标识符。`params` 中的模型参数采用 `{name, values}`，省略条件遵循上述参数规则。`extraTables` 只用于契约明确支持的附加表，不得绕过模型治理。

示例中的 `SUM` 只适用于已确认可加的度量；使用前核对底层列和模型公式。语义时间层级不一定是实际存储列，示例日期必须改为用户所需范围。

### 解析 SQL 的 FROM

SQL 的 `FROM` 使用数据模型逻辑表或视图别名，不用物理表名，须从当前模型元数据解析。有些模型的逻辑别名与字段树中的来源或度量文件夹别名一致，也可用于 `mql.from`；这只是模型特定现象，不能通用化。

只读 SQL 出现 `DAO_ID_IS_NULL` 时，先核实 `FROM` 是否能在模型中解析，不猜物理表名或盲改列名。元数据无法给出可用逻辑来源时，应说明信息不足。

`年`、`年季`、`年月` 等语义时间层级可能不是逻辑事实表的物理列。已确认日期列时，可用 `year("<DATE_COLUMN>")` 等 DuckDB 函数生成所需层级，不假定存在同名基础列。

## MQL

操作：`datamodel.queryDataByMql`
HTTP: `POST /api/v1/datamodel/datamodel/query-data-by-mql`
请求体：外层为 `req` 对象：

```json
{
  "req": {
    "modelId": "<MODEL_ID>",
    "modelType": "<MODEL_TYPE>",
    "mql": {
      "from": "<MODEL_SOURCE>",
      "dims": ["年"],
      "metrics": ["<ADDITIVE_MEASURE>"],
      "dimFilter": "\"年\" >= 2022",
      "metricFilter": "",
      "sort": [["年", "ASC"]],
      "limit": 100,
      "offset": 0
    },
    "params": [],
    "showDataTable": true
  }
}
```

只使用上述查询元数据已确认的维度、度量、来源和筛选字段。契约要求层级路径时须保留完整路径，如 `客户维.分公司名称`，不能改用未经限定的技术字段名。`dim_cust_info` 等物理表即使出现在模型定义里，也不能据此认定它是有效的 MQL `from` 或 SQL `FROM`。目标部署支持 `mql.with` 时，可定义计算列、基础度量和计算度量；计算度量表达式采用 MDX 语义，不是 SQL。

按当前 MQL 契约、已核实的维度路径和值类型构造 `dimFilter`。字符串比较、层级路径及条件组合均以目标模型契约为准；不要把个别模型的字段名或表达式能力推断为通用规则。成员值或编码不确定时，可先做一次有界的无筛选分组查询确认候选值；已核实值域时不重复调用。未核实值域而过滤结果为 0 行时，只能报告“返回 0 行”，不能断言业务数据不存在。

同一个查询表达式的 MQL 构造尝试最多两次：首次执行及一次有元数据依据的修正。仍有歧义时向用户澄清，不继续猜字段或成员。合法分页、已确认的独立查询组及必要总计核对不属于修正试错；明确的能力不支持、权限或数据源异常按实际原因处理，不要求用户澄清技术错误。

度量公式、原始列映射、关系、参数或来源别名不足时，按上述补充条件读取完整定义，不重新发现操作。SQL `FROM` 使用模型契约确认的逻辑视图别名，不把物理表名或内部 `name` 直接当作查询标识。

跨来源的模型级计算度量应按模型公式及已核实契约处理。MQL 的 `from` 可选，不要给根级度量虚构单一事实表来源；组成项须在相同筛选和粒度下核验。模型明确定义的公式优先于从业务名称推测的算法。

`with` 和聚合表达按当前契约与模型引擎能力构造。请求符合契约但执行异常时报告接口问题，不通过更换聚合算法、拆分指标或自动切换接口取得结果。需要其他计算方式时，按用户要求及场景选路重新确认其业务口径。

模型定义本身不保证业务标签正确：名称像金额的度量可能实际采用 `COUNT`。若定义与用户问题冲突，先说明并确认目标度量，不静默更改聚合方式或直接交付金额结论。

中位数、分位数的统计约定会改变答案时，应核实偶数样本中位数及连续／离散分位数算法。运行成功和落在最小／最大值之间，不证明算法符合预期。若能取得完整且有界的原始样本，可独立计算并说明差异；否则明确验证限制。本地计算须说明方法与数据完整性，不能伪装成 MQL 原生结果。

需要来源时，`mql.from` 应使用包含目标度量的模型逻辑视图／来源别名，不自动使用模型名称或别名。模型级计算度量按上述可省略来源的规则处理。多个来源候选时，根据字段映射和指标定义确定实际来源；不能唯一确定时补齐定义或澄清，不按候选逐个执行查询。

分组、跨来源关联及对账要求见[模型语义与结果校验](query-semantics.md)。

## 执行与结果校验

先按[公共结果规则](../common-core/query-results.md)检查业务状态与范围，再核对本次模型字段、参数和粒度。请求与契约不符且有依据时修正；符合契约仍失败或结果与同口径证据矛盾时，保留错误及影响范围，不换模型、引擎或查询接口掩盖。接口诊断不作为每次业务查询的前置，耗时见[公共排障](../common-core/troubleshooting.md#直接取数耗时)。

## 结果处理

默认取数范围、部分结果说明和分页终止原则统一见[公共结果规则](../common-core/query-results.md)。JSON 使用上文的 iterator 和分页参数；MQL/SQL 按 dataTable.data 的实际行数处理，稳定排序与批量保持不变。rowCount 可能大于本页行数，须确认它在当前契约中的含义，不能直接作为已交付行数。

MQL 顺序分页使用固定页长及 `offset = 从0开始的页序号 × limit`，检查相邻页无重复或遗漏；不把该 offset 规则套用到 JSON 的 rowPageNum 或 SQL 文本。没有稳定排序、查询期间数据变化或结束证据相互矛盾时，明确完整性限制。

MQL/SQL 接口返回 `modelId`、`s3Url`、`rowCount` 和可选 `dataTable`。检查 CLI 执行状态及业务层 `success/error`。`s3Url` 非空时按当前 SDK 契约下载，并核验真实字节与文件格式，不只凭后缀判断 Parquet。`s3Url` 为空时，只有核实请求范围与分页结束，`dataTable.data` 才能作为有界查询的完整结果；单靠 `rowCount` 不够。页面达到 `limit` 时继续稳定分页；无法确认取齐时标明已交付范围只是部分数据。聚合或合并前按 `references/model-query/query-semantics.md` 校验比率和时间粒度。

AVG、比率等指标若声明为整型或零位小数，返回值可能损失计算精度，不能据此认定真实均值为整数。确需更高精度时，按已核实的同口径原始值、SUM/COUNT 复核；用户明确指定 SQL 时也可使用只读 SQL，分别说明模型显示值与复算值；合并分组均值须有有效样本数，不能直接平均各组均值。

同一任务中，环境、身份和模型定义仍适用时复用已确认的元数据与操作契约；完整模型定义不是默认前置，也不写为 Skill 持久缓存。来源、筛选、时间粒度和聚合语义一致时，才将兼容度量合并查询。合并请求失败时按原始错误判断受影响范围，不自动拆查以掩盖失败，也不推断全部度量均不支持。查询耗时与工具超时按 `references/common-core/troubleshooting.md` 诊断，不把历史耗时当作跨环境基线。
